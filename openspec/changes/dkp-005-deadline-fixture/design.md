## Fixed TLS response gate

The proposed external relay is part of the attested fresh fixture, never a public business route. KB keeps its normal fixedHTTPS DM adapter. The relay has one exact preconfigured DM upstream/CA/hostname; it permits only POST `/api/v1/documents/knowledge-share-assessments` and POST `/api/v1/documents/knowledge-share-eligibility`, with existing bounds, plus separately fixed readiness routing if the selected composition requires it. No caller URL, arbitrary proxy, redirect, decompression, replacement payload or forged response is accepted. Authorization and selected-tenant bytes are forwarded unchanged only to actual DM and never logged. Every successful gate result must originate from actual authenticated production DM; mock JSON cannot satisfy acceptance.

Gate INITIAL and FINAL separately per private actor/request association; prove exactly two ordered calls for a nonempty strict/eligibility operation, reject duplicates/extra/reordered/unbound calls. A single case may hold at most one genuine response per actor and at most16 across the instance; retained response bodies are each<=32768 bytes, so body storage<=524288 bytes, excluding explicitly measured transport/runtime overhead. Inbound request bound remains16384 bytes; total transient memory must be measured separately. No unbounded waitlist or response replay. A gate cannot extend the application's deadline. Controller waits, relay upstream I/O and teardown have explicit monotonic finite deadlines selected and tested in the implementation packet; control timeout fails the case and cannot become an application success.

Release is a one-use owned control operation over private local transport; unrelated UID, foreign run, stale phase or duplicate release must fail. The relay buffers no more than the allowed response, preserves status/body/content-type bytes, refuses encoding/oversize/redirect, and records only bounded digest/timing/counter evidence publicly. Delayed genuine ALLOW after caller abort/deadline is a negative stimulus, never a grant. Forward/cancel completion is not proof that the KB worker or SQL settled.

## Real clocks, local locks and attribution

Use one monotonic controller origin per case. Record initial/final relay arrival, genuine DM upstream completion, gate release, client response/disconnect and independent KB/PG settlement; retain exact wire/status/data digests privately. Never reset a service clock, set shorter product constants, or infer production elapsed time from injected clocks. A relay delay is labelled injected transport delay, not native DM processing time. A late-client response does not prove late COMMIT, and fast503 alone does not prove which inner deadline fired.

A separate trusted controller connection may hold exact existing owned KB rows using ordinary transactions: tenant fence, then collection and document-scope locks in actual production order. It performs no domain DML/schema/trigger/function modification. Release barriers follow real pg_locks/pg_stat_activity observations, not sleeps. Sequential waits below individual250ms may expose cumulative500ms exhaustion; preexisting initial reads must complete before the final barrier takes its locks. Authority/catalog work is included in the existing local500ms source clock; external observation cannot silently exclude it.

Report observer scheduling/transport uncertainty explicitly. Only an upper bound whose complete uncertainty interval is within the selected limit is evidence of an on-time acknowledgement. If clock boundaries cannot be mapped to exact DM dispatch/KB acknowledgement, report INCOMPLETE rather than assigning wire time to an internal phase. Exact before/at/after component guards remain necessary but do not replace deployed timing evidence. Admission50ms is measured at its actual boundary; a client roundtrip includes authentication/transport and cannot be mislabeled admission latency.

## Pool observation: research candidate, not selected

The exact supported Hikari APIs and Java25 local management research are in research.md. A candidate fresh-only one-property `hikaricp.configurationFile` could request `registerMbeans=true` without a business hook; the manual production factory's explicit pool identity/limits/credentials must remain unchanged and no other properties may enter. Hikari registers both pool and configuration beans, exposing mutating capabilities as well as getters. A read-only collector is NOT a read-only management server. No broad unauthenticated/remote management endpoint, privilege/capability increase, custom agent, reflection repair, bean setter/invoke, eviction, pool suspension, class loading or heap/property dump is allowed.

Only after separate explicit selection/review could a fixed same-UID/same-container Java25 Attach collector request the standard local management agent and read the exact attested `kb-runtime` pool's numeric ActiveConnections via supported API. No activation occurs under422. Local management still creates a management surface; implementation would have to prove same UID, private attach files, loopback-only connectors, no published/network-reachable listener, exact target PID/start identity/image and safe shutdown. If this cannot be enforced without weakening existing container controls, reject it. Do not alter attach flags/security, add SYS_PTRACE/root/host namespaces, or enable a remote port to make it work.

MXBean ActiveConnections directly observes borrowed/in-use count at an instant. Idle/active/total are independently transient, not an atomic tuple. For the required deterministic ownership case, hold a genuine initial/final HTTP response pending at the owned relay and validate the same actual production factory/pool with a positive blocked-SQL control showing ActiveConnections>0. While the target worker is demonstrably awaiting that response, an ActiveConnections=0 observation disproves a connection being retained ACROSS that pending wait. Pair this with attested source/class ownership/order review, no PG transaction/locks, isolated traffic and timestamp uncertainty. The gate stays OPEN until actual direct positive/negative deployed evidence exists. A short borrow between samples remains undetected: continuous absence at every instant is NOT CLAIMED and is not invented as an additional368 exit criterion. Component datasource wrappers, PostgreSQL idle status, source inspection alone or a null/unregistered bean cannot replace the direct deployed observation.
