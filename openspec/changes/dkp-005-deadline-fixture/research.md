## Exact supported Hikari surface

- The [official7.1.0 release](https://github.com/brettwooldridge/HikariCP/releases/tag/HikariCP-7.1.0) identifies the existing release; its tagged [license](https://raw.githubusercontent.com/brettwooldridge/HikariCP/HikariCP-7.1.0/LICENSE) is Apache2.0. No new library is introduced. Research binds the reviewed release source rather than moving dev/main.
- The tagged [HikariPoolMXBean](https://raw.githubusercontent.com/brettwooldridge/HikariCP/HikariCP-7.1.0/src/main/java/com/zaxxer/hikari/HikariPoolMXBean.java) exposes `getActiveConnections()` and three other numeric getters. Its documented counts are transient independent observations. It also exposes eviction/suspend/resume operations; possessing the whole management interface is not a read-only server capability. A zero count directly observes no in-use connection at that instant, not an interval-complete trace.
- The tagged [HikariPool implementation](https://raw.githubusercontent.com/brettwooldridge/HikariCP/HikariCP-7.1.0/src/main/java/com/zaxxer/hikari/pool/HikariPool.java) maps active count to the bag's in-use count. Borrowing precedes returning a proxy; return eventually requites the entry. This distinguishes an idle DB session with a borrowed proxy from one returned to the pool. Count sampling can miss a short borrow/return between observations. No SQL activity inference fills that gap.
- The tagged [HikariDataSource](https://raw.githubusercontent.com/brettwooldridge/HikariCP/HikariCP-7.1.0/src/main/java/com/zaxxer/hikari/HikariDataSource.java) has the public `getHikariPoolMXBean()` accessor. It requires the actual datasource instance in the same JVM and can be null before initialization for the lazy constructor. This does not expose an already-running application's private instance to an external process. Reflective heap discovery or a custom injected agent is outside this proposal.
- The tagged [HikariConfig constructor](https://raw.githubusercontent.com/brettwooldridge/HikariCP/HikariCP-7.1.0/src/main/java/com/zaxxer/hikari/HikariConfig.java) can load an ordinary property file from standard system property `hikaricp.configurationFile`. A fixture-only exact file containing solely `registerMbeans=true` is therefore a candidate for registration without changing a business factory hook. All other settings would remain rejected/absent from this file. This is not selected/activated here; configuration parsing/failure behavior and effective unchanged runtime properties need causal tests before use.
- The tagged [PoolBase registration](https://raw.githubusercontent.com/brettwooldridge/HikariCP/HikariCP-7.1.0/src/main/java/com/zaxxer/hikari/pool/PoolBase.java) does nothing unless registration is enabled. It registers both pool and configuration beans; legacy names include the exact configured pool name, while a separate system property changes naming convention. A future collector must attest one fixed naming convention, pool instance and startup identity, not query arbitrary beans or accept a similarly named foreign pool. No setter, operation invocation or configuration repair is permitted.

## Exact Java25 public management surface

The [Java25 management guide](https://docs.oracle.com/en/java/javase/25/management/monitoring-and-management-using-jmx-technology.html) documents local Attach management without a startup remote-port flag and same-user access controlled by operating-system permissions. It distinguishes remote management activation and related security controls. Local management still changes the JVM's available management surface; it is not proven safe merely by omitting a published Compose port. Loopback/container namespace/attach-file identity and forbidden remote properties require actual negative tests. This research does not configure JMX, relax TLS/authentication or introduce a public listener.

The [Java25 VirtualMachine API](https://docs.oracle.com/en/java/javase/25/docs/api/jdk.attach/com/sun/tools/attach/VirtualMachine.html#startLocalManagementAgent()) provides `attach`, `startLocalManagementAgent` and `detach`. Standard local-agent startup is a supported candidate, distinct from loading a custom agent. Attach also has broad agent/property operations; proposed collector code must be fixed and restricted to the chosen local startup, exact numeric getter reads and detach. A client allowlist does not constrain every other same-UID management client; no server read-only guarantee is claimed. Runtime access may fail because of image/module/attach/filesystem/container policy and must remain unavailable without flags/privileges fallback.

## Current-source finding and decision

At inspected c2b7305, KnowledgeRuntimeFactory constructs HikariConfig manually and then HikariDataSource with fixed `kb-runtime`, maximum16, minimumIdle0 and acquisition/validation250ms. It does not request bean registration or activate a management connector. Direct external bean observation is therefore NOT available by default. The supported property-file candidate avoids a business hook but requires separately reviewed attested startup material; it also exposes the configuration bean. No candidate is automatically allowed because its API is public.

Research conclusion: direct fixed pending-wait borrowed-state evidence is technically plausible using supported pinned APIs. A genuinely pending response plus same-pool ActiveConnections=0 can disprove retention across that wait; a same-factory positive SQL control must first show active>0. Source ownership/order and timing uncertainty are part of the claim. No deployed proof exists yet. D01 access selection, D02 exact boundary proof, D03 immutable implementation/resource/control profile and D04 independent settlement remain unresolved. The required across-wait gate stays OPEN. PostgreSQL activity/component wrappers cannot substitute. Continuous absence between samples is not claimed or imposed as a new368 gate.
