# Processing protocol recovery — proposed correction259

This document is normative within the unapproved draft. It resolves review253; it does not authorize implementation or production release. All three workload routes are closed, private mTLS POSTs with16KiB requests,32KiB responses and2s whole deadlines. Existing actor/workload policy, no network under SQL, original30minute deadline and50-slot conservation remain unchanged.

## 1. Server-issued attempt and start ordering

The immutable workflow input remains free of mutable attempt/revision fields. Its fingerprint is lowerhex SHA256 of UTF8 [RFC8785 JCS](https://www.rfc-editor.org/rfc/rfc8785) bytes of the complete schema-valid input object, without a newline. The stage input digest is SHA256 of JCS `{workflowInputDigest,stage:"RESOLVE_ORIGINAL_V1",contractVersion:"1.0.0"}`. Java/workflow producers must pass shared canonicalization fixtures before rollout; no language-specific map iteration digest is permitted.

Before any possible Temporal Start dispatch, one DM transaction reserves the active permit, persists the exact logical workflow identity/input fingerprint, allocates the RESOLVE_ORIGINAL_V1 stage attempt and epoch, and marks remote-start-may-exist. Dispatch claim lease epoch and stage attempt epoch are separate columns: taking a reconciliation claim never invalidates a live activity. An epoch advances only by a DM-owned stage transition after previous promotion rights are fenced. Lease expiry alone permits neither a second execution nor release of capacity.

An activity knows its actual logical workflow ID and Temporal execution run ID from the activity context, and its immutable input. It calls `/attempt-handoffs` with those identifiers, the input digest and fixed stage; it supplies no epoch, revision, actor or tenant. DM authenticates the exact allowed workload/stage and re-evaluates the stored accepted actor's current tenant/action/catalog/ACL. Before SQL, it queries the exact trusted Temporal namespace/execution and bounded first WorkflowExecutionStarted history event, validates the schema-valid original input fingerprint and allowed workflow deployment/type. An unavailable, truncated, wrong or contradictory observation is503/denial, never inferred from a caller assertion. Evidence beyond the2s bound fails closed; no background SQL may follow expiration.

In one fenced transaction DM binds the verified execution ID to the pre-existing attempt. A worker that reaches DM before the dispatcher's Start acknowledgement may complete this binding: it reconciles the same possible execution, not a new Start. A lost acknowledgement/process crash follows the same path. The later dispatcher acknowledgement must agree with the bound execution/input and cannot increment the stage epoch, rewind run state or duplicate an event. A different execution ID/fingerprint is a conflict, retains possible-start capacity and blocks promotion. A deterministic workflow restart/replay keeps the same execution identity; a new Temporal execution cannot silently inherit this attempt.

The response returns current server-issued `attemptEpoch`, `expectedRunRevision`, fixed `inputDigest` and either null or the original committed compatible checkpoint receipt. Repeated handoffs return the current fence after fresh validation, not a fabricated default0. If another internal transition advances the run revision, the worker reacquires a handoff without changing epoch. Cancelled/expired/revoked or unknown authority cannot obtain a usable attempt. No DISPATCHED-after-Start prerequisite deadlocks an early worker; the durable pre-Start attempt is the prerequisite.

## 2. Immutable resolution and checkpoint recovery

`original-resolution` still requires the current handoff epoch/revision and fresh workload plus accepted-actor authority. Resolve verifies the exact persisted version/object/evidence and current policy before/after remote metadata I/O. In bounded SQL it persists a server-issued immutable resolution keyed by `(tenant,run,stage,contractVersion,inputDigest)`, with a unique resolutionId and the canonical closed resolution payload/hash. The first observedAt is immutable. Volatile attemptEpoch and runRevision are request guards, never resolution payload identity. Retries do not create a fresh timestamped result.

Checkpoint requests contain only the current epoch/revision, inputDigest and resolutionId; they cannot upload replacement observations. DM reloads and validates the exact server resolution, input/profile/producer/lineage and current policy. First insertion requires current CAS/fence and atomically commits checkpoint, run transition, audit and event. Checkpoint uniqueness is `(tenant,run,stage,contractVersion,inputDigest)` across epochs. Resolution facts remain immutable; no overwrite on retry.

On an existing exact checkpoint, re-evaluate current workload/actor/tenant/ACL, original deadline/cancellation state and current epoch compatibility before replay. A stale expectedRunRevision from the exact already-committed request does not prevent returning the original200 receipt. A retry from a newly issued compatible current epoch may return that same immutable checkpoint; its receipt runRevision is explicitly the original committed revision, not current CAS permission. No new checkpoint, audit, event or revision is produced. A stale epoch cannot create an absent checkpoint; a different resolutionId/input under an existing semantic key is409, not a payload replacement. Unknown current policy/trust is503; revoked/hidden is404; cancellation/deadline forbids stage continuation. Handoff/replay is not an artifact grant.

Crash after resolution commit/lost resolve response: re-handoff, fresh authorization, resolve returns the exact stored result. Crash after checkpoint commit/lost200: handoff exposes the original checkpoint receipt, or repeating its exact checkpoint request returns original200 after fresh checks. The workflow must not rerun side effects merely because acknowledgement was lost. If the checkpoint becomes incompatible, block and reconcile rather than consume it. A new epoch may reuse a positively compatible checkpoint but never let an old callback promote state. These rules also apply after process/database restart and restored histories; they do not claim network cancellation proves absence.

## 3. One explicit processing-event aggregate

All four event types use `aggregateId = processingRunId`. `aggregateRevision` is a separate contiguous per-run **event sequence**, beginning1 at acceptance/enrollment; it is not documentRevision or runRevision. The payload includes explicit runRevision and documentRevision observations. Every event-producing transition increments the event sequence and inserts exactly one immutable envelope atomically with its effect. Claim renewals and other non-event operational updates do not consume sequence numbers. Internal run transitions do not advance document metadata revision. Cancellation may advance both business revisions but consumes only the next event sequence. Stable event IDs and causation remain unchanged on relay retry.

Kafka key remains documentUUID to preserve the existing document partitioning proposal. Multiple run aggregates can interleave on that key. Consumer inbox identity is eventId+payloadhash; ordering/gap scope is `(tenantScope,aggregateId)` and uses aggregateRevision only. Never compare different runs' sequences or infer a gap from unrelated document metadata updates. Duplicate sameID/hash applies once; sameID/differenthash or same aggregate sequence/different immutable event conflicts. Contiguous next sequence applies atomically; higher sequence buffers boundedly and triggers authoritative run/event-watermark reconciliation. Recovery must not invent a missing transition from a current state snapshot. Lower sequence with unknown eventID requires authoritative reconciliation, not a second effect. Outbox uniqueness `(tenant,run,eventSequence)` and constraints bind envelope aggregateId/payload runId/document/version/profile and both revision observations to the transaction.

The standalone event schema and AsyncAPI embedded payload are identical. The public direct/BFF run status revision remains runRevision, with existing mirror schemas unchanged; event sequence is an internal ordering contract. Legacy201/minimal receipts and all compatibility witnesses remain untouched.
