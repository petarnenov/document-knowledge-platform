# DKP-006 design — candidate development baseline, unapproved

## 1. Authority and architecture
The public System Design5/6/7/8/12/13/14 and acceptance.md govern. BP03 correction242 and BP04 real integration are prerequisite runtime gates. No provider/data change is authorized by this draft. DM owns document/version/receipt/run/intent/outbox/command/audit state; Processing owns execution/checkpoint/artifact production, never publication. Temporal owns its execution history in its own infrastructure persistence, not the DM schema. Kafka is event transport, not a processing command queue. KB/Search retain separate logical databases, credentials, migrations/outboxes. No distributed transaction is claimed.

Domain/application remain framework-free: ProcessingAcceptancePort/UoW, ProcessingIntentRepository, ProcessingDispatchPort, RunObservationPort, CheckpointPort, EventOutboxPort, WorkloadIdentityPort and current authority/artifact ports use immutable semantic values. SQL/Temporal/Kafka/network mappings live in adapters. Dispatcher/relay run separate images from HTTP DM; a separately built processing worker implements deterministic orchestration plus real I/O activities. Shared modules contain versioned technical envelopes only, never live cross-service entities. No workflow or worker directly reads another service's tables.

## 2. Atomic acceptance and unchanged legacy surface
New POST /api/v1/documents/{documentId}/processing-acceptances takes exactly the existing AppendVersion body{expectedRevision,receiptId}, trusted bearer+tenant selector+idempotency. It requires current document.version.append catalog AND documentACL, exact original actor/tenant/document receipt ownership, current immutable verification facts, no unresolved copy/writer/deletion fence and exact RustFS object version/hash/size. It derives IDs, profile/image/schema digests and timestamps server-side. A client supplies no objectkey, tenant, processing status, trusted hash, reviewed classification or executable profile.

Outside SQL: authenticate/current membership, initial policy, load verified immutable evidence. Inside one bounded DM UoW: tenant/document/receipt/key locks in existing BP03 global→tenant→document→slot→receipt/outcome order, check CAS/current local authority and integrity/evidence generation, append immutable version, reserve one initial run, insert unique intent plus one DocumentVersionAccepted event, consume receipt, update document revision, append audit and command. No Temporal/Kafka/S3 HTTP or file inspection occurs under SQL locks. Lock-sensitive external policy generation is reread before transaction and final boundary; changed generation/current denial aborts or withholds result, never assumes global cross-system atomicity. Existing BP04 local authority adapters can reread local immutable catalog under SQL only when no network is involved.

All four business records and receipt consumption/command/audit commit or roll back together. Only then may202 return {documentId,versionId,revision,processingRunId,status:ACCEPTED_PENDING_DISPATCH}. That is the durable acceptance receipt, never a claim about current Temporal execution. UNKNOWN COMMIT yields finite503; original key/body retry reconciles persisted outcome after current authority, with no second version/run/intent/event. A delayed callback cannot enter SQL after its request deadline. Receipt single consumption holds across new and legacy route keys.

Legacy dmAppendVersion and bffAppendVersion keep exact path, method, AppendVersion DTO, original201 CommandReceipt fields and semantic operationIds. Pre-cutover original keys return their original201 after current authorization, never retroactively create a run. Post-cutover NEW legacy commands call the SAME atomic-four-record use case and project its documentId/revision as201. Legacy client-visible success still means append acceptance only; new status APIs disclose processing state only with separate current inspect authority. The legacy route needs its existing append action, not a newly required role, so old valid client grants do not silently break. This explicitly adds durable processing scheduling to new legacy appends; independent review must accept that compatibility migration before cutover. Freeze a deployment feature barrier so no new append can commit a version-only record after activation. During mixed release rollout, old writers are fenced by database cutover generation; fail503 rather than admit partial writes.

## 3. Existing version coverage and immutable lineage
Every pre-cutover version is durably inventoried by tenant/document/version and labeled NOT_SCHEDULED; inventory watermark and current coverage are complete before enabling cutover. Do not skip old versions, auto-claim READY or bulk-rewrite versions. GET version/processing returns NOT_SCHEDULED with nullable run reference, or the exact linked run. New POST version/processing-runs explicitly enrolls an existing version and requires current document.processing.request AND original append catalog/ACL authority, CAS and current trust/retention assessment. It creates run/intent/outbox/command/audit atomically with a reference to the already immutable version and returns a distinct202 receipt. This is not falsely represented as NEW-version atomic acceptance. Unavailable/missing/nonreusable original evidence fails503 without a run; known malformed/ineligible evidence is422. A necessary revalidation/rescan must use the existing isolated verifiers; no forged success, dropped format or trust bypass.

Unique initial run per tenant/version prevents duplicate enrollment across migration, legacy and explicit commands. No later reprocessing generation is invented here; future profile migrations require a separately reviewed API. Existing original byte evidence, submitted classification, creator/time, active pointer, approvals and review state remain unchanged. Scheduling changes no active publication pointer. Run/current authority views remain privileged draft administration, not end-user content access. Workflows do not gain content rights from an old receipt or acceptance response.

## 4. Durable claims, deterministic identity and start ambiguity
Intent states PENDING_DISPATCH→CLAIMED→DISPATCHED; retryable UNKNOWN/PENDING carry nextAttemptAt, attempt count, exact claim owner/epoch/deadline. Terminal CANCELLED/FAILED evidence is retained. Claim uses SKIP LOCKED bounded batches and persistent global+tenant admission; no remote calls inside claim transaction. Candidate lease30s, renewal10s, dispatch RPC<=5s, sweep1s, claim batch<=10. Start only after committing claim AND the pre-Start stage attempt/input fence described in protocol-recovery.md; claim epoch and stage epoch are distinct. Workflow ID is dkp-processing-v1/<opaqueRunUUID>, unique in fixednamespace dkp-development; no raw tenant/actor/title in routing/search attributes. Deterministic ID, input fingerprint, profile digest and version binding are stored before any start call. Use REJECT_DUPLICATE closed-ID reuse and FAIL running-ID conflict, never terminate or reuse a conflicting execution.

Start timeout/EOF/AlreadyStarted is AMBIGUOUS, not absence. Describe exact namespace+workflow ID and validate execution input/type/profile fingerprint through a bounded authenticated read/protocol. Same identity reconciles DISPATCHED; different identity fails503/quarantined operational alert, never attaches someone else's run. Describe-not-found after timeout alone is not proof no delayed start can occur: continue same deterministic ID, no freshrun-ID creation. Persist permanently which run ever used that ID so Temporal retention/deletion cannot permit duplicate start. An unresolved start keeps its global50 permit; after service restart lease expiry transfers reconciliation ownership, not permission to invent a new workflow. Stale claim results cannot mutate state. A reconciler checks durable intent, Temporal history and execution status until bounded observation resolves or explicit operator repair, never deletes evidence to free quota.

## 5. Real deterministic workflow skeleton and bounded execution
The real Temporal workflow type DkpDocumentProcessingV1 accepts only closed server-derived run/artifact references, provenance and digests (workflow-input.schema.json). No bearer, cookies, raw content or arbitrary URL. It performs a real authenticated ResolveOriginalV1 activity: resolve authorized exact DM artifact metadata, independently validate lineage/evidence compatibility/current scoped workload authority, and persist an idempotent DM-owned checkpoint via fixed internal boundary. No arbitrary original bytes are copied into workflow history. A valid checkpoint proves only original resolution, never parsing/readiness. If the approved parse capability is absent, state WAITING_FOR_CAPABILITY with reason PARSE_NOT_INSTALLED is visible and durable. No dummy successful parse/activity or READY/COMPLETED outcome is allowed. The original30minute clock includes this wait; a real durable timer initiates safe timeout/cancellation and terminal reconciliation. Provider absence does not reset that deadline. Future BP06–BP12 replace the registered capability implementation through versioned activity contracts, not untrusted code download.

Workflow code performs no SQL/network/clock/random I/O except deterministic Temporal APIs. Activities are idempotent using(runId,stage,contractVersion,inputDigest); successful immutable compatible checkpoints are reused after crash, incompatible producer/schema/profile/classification/tenant/residency/retention facts are not reused. Separate fixed task queues processing-control-v1, parse-ocr-v1, chunk-v1, embed-v1, graph-v1, index-v1, preview-v1 reserve later stage contracts without claiming their execution exists. Candidate first real ResolveOriginal activity start-to-close10s, schedule-to-close30s, heartbeat2s where streaming, retry initial1s/max10s/backoff2/max5, total bounded by original run deadline. Heavy-stage concurrency is not inferred from50 workflow slots. No workflow-level automatic retries create a new logical run. Replay-test history and pinned worker deployment ID/digest prevent nondeterministic upgrades; old histories retain compatible worker until drained.

Global max50 active workflows/ambiguous starts is persistent in DM; max5 per tenant proposed, tenant FIFO with round-robin ready tenants, actor/API admission1/global16. Capacity is released only after authoritative exact terminal observation plus no running stage callback; expired lease alone never frees it. Accepted durable intents may queue boundedly: max1000 pending globally/100per tenant; exceeding quota429 before version/receipt mutation. Temporal outage leaves accepted PENDING; Kafka outage independently retains outbox; one dependency never fakes the other. The global50 baseline and30minute maximum are public requirements; candidate tenant/pending budgets require review and actual fairness/multi-dispatcher tests.

## 6. Cancellation, holds, stage fences and UNKNOWN
Cancellation is a durable actor-authorized command, not synchronous proof of stopped work: require document.processing.cancel+currentACL, CAS/current membership and idempotency, commit CANCEL_REQUESTED+intent/outbox/audit. A current start attempt and cancellation are serialized with exact run fence: before start, cancellation can prevent dispatch; after possible start, signal/cancel same workflow and reconcile. A late acknowledgement cannot revert terminal/cancelled state. Each activity gets attempt epoch and checks current cancellation/authority immediately before effects; stale output may be retained only as private orphan evidence for bounded cleanup, never promoted/reused as current result. SQL claim expiry is not remote execution termination.

Cancellation/timeout never purge originals, consume new receipts, modify historical versions/approvals or release storage charges blindly. Retention remains unresolved development policy; active hold/unknown hold/eligibility prevents destructive cleanup. Reuse requires positive current retention eligibility; lack of approved lifecycle policy is not deletion permission. No new destructive artifact cleanup protocol is hidden in BP05. Known/private temporary spools follow existing trusted bounded cleanup; unknown side effects retain accounting and durable repair work. A run remains CANCEL_REQUESTED/TIMED_OUT_RECONCILING until termination and no-late-effect proof; only then CANCELLED/TIMED_OUT. Worker shutdown, partial network responses, crash/restart and physical client cancellation are tested separately. API cancellation controls the accepted command response, not a durable committed run's existence; reconcile by original key.

## 7. Outbox and Kafka remain independent
Acceptance inserts the closed versioned DocumentVersionAccepted envelope in the same transaction. Each row stores immutable eventId/type/schema/aggregateId/revision/time/actorRef/tenantScope/correlationId/causationId/payload. Payload references version/run/intent/profile identifiers and explicit runRevision/documentRevision observations, never original content, metadata titles, tokens or object credentials. Audit is separate append-only security evidence; telemetry is separate again. Topic dkp.document-events.v1, key opaque documentUUID, maximum encoded envelope16KiB; consumer validates schema and independent workload scope before any derived work.

Relay claims oldest unsent per aggregate with lease/epoch and sends outside SQL. Kafka producer enable.idempotence=true, acks=all, max.in.flight=1, retries bounded by delivery.timeout.ms10000, request.timeout.ms5000, max.block.ms5000, TLS hostname verification and scoped producer ACL. Broker replication3/min.insync2 for staging/production proposal; one-broker local profile is explicitly non-HA and must not be sold as durability/DR proof. Ack then fencedSQL mark: crash after publish before mark causes sameeventId redelivery. Kafka transactions/idempotent producer do not atomically include PG; no exactly-once cross-system claim. Consumer inbox stores eventId+aggregate/revision+payloadfingerprint atomically with its owned effect. Duplicate sameID accepted once; different payload sameID rejected; gaps/out-of-order are buffered boundedly and reconciled against authoritative run event sequence/watermark and immutable missing envelopes, not inferred solely from a current state snapshot. Relay never routes an intent through Kafka. Failure never silently drops/deletes outbox; backlog quotas429 newacceptance before commit and observable lag.

## 11. Review253 protocol corrections (issue259)

Contracts/protocol-recovery.md is normative: three closed workload routes include server-issued attempt handoff; stage registration precedes possible remote Start and authoritative execution binding handles early worker/lost ACK without a second Start. Immutable resolution/checkpoint identity excludes volatile observation guards; fresh-authority replay returns the original committed result across compatible epochs. All processing event envelopes use runUUID aggregate identity and contiguous eventSequence, with explicit runRevision/documentRevision payload observations and documentUUID Kafka keys. There is no implicit worker bootstrap, timestamp-sensitive checkpoint replay or document-revision gap heuristic. Contract protocol fixtures are specification examples, not implementation tests or runtime proof.
