Development implementation baseline accepted by independent171/172 specification review and recorded in approval.md. Actual timing, concurrency, race and E2E acceptance remain pending. It replaces the rejected10-way/55-second multiple-request proposal; none of those older numbers or24-second windows is an implementation permission. No production revocation, workload, CID07 or capacity approval is claimed. New KB routes/BFF use these candidates; existing DM metadata3-second gateway and BP03 routes remain unchanged.

## Explicit single-instance capacity

At both KB batch-bearing request admission and BOTH DM strict/eligibility endpoint admission, allow at mostONE in-flight batch-bearing request per exact authenticated actor(issuer,subject), across its tenants, and at most16 such requests globally per PROCESS. Acquire atomically within50ms or return503 without queued work; release permits on bounded completion/failure. Replays are not exempt. KB performs initial then final batch sequentially, so its own phases do not overlap the actor permit. Pure collection reads that require no DM batch do not reserve this batch capacity; they still have the8-second deadline and bounded DB requests. An empty affected member set makes no empty/pretend DM call, but must be proved unchanged by final local checks.

These are explicit development SINGLE-INSTANCE limits. Multiple KB/DM instances each have their own counters; no fleet-wide or distributed semaphore guarantee is invented. Production scaling/abuse control remains separately reviewed. Each strict or eligibility batch always contains<=100 DISTINCT document UUIDs; duplicates fail422 before resource lookup, and no item schedules another HTTP request. Thread/connection pools are bounded by the16 admitted requests. No scalar ResourceAuthorizationPort loop, unbounded async fanout or fallback retries may masquerade as one coherent batch.

## DM-owned coherent batch authority

The new actor-authenticated POST `/api/v1/documents/knowledge-share-assessments` accepts1..100 canonical documentId/optional expectedDocumentRevision entries for one independently verified caller and selected tenant. Its response binds that exact actor/tenant/action and exact complete set. Every item passes current document.share-to-collection operation grant AND DM ACL ALLOW/noDENY. Missing/denied document gives one uniform404 for the whole batch; no per-item failure, missing index/count, partial rows or selected subset is returned. Unknown/malformed authority503. Expected revision conflict409 occurs only after the complete set passes current authorization. Supported development classification is checked for all returned items.

DM application owns a new `DocumentShareBatchAssessment` use case and a distinct `RequestScopedResourceAuthorityPort`; KB application owns `DocumentShareBatchAuthorityPort` implemented by the fixed HTTP adapter. Existing scalar ResourceAuthorizationPort cannot be declared coherent merely by calling it100 times. Proposed technical port input is exact actor/tenant/action plus the complete bounded document set; output is an immutable request-scoped snapshot containing exact binding, every decision and an internal validated-catalog fingerprint. Standalone implementation reads/validates the whole bounded trusted catalog ONCE for that snapshot, including all ancestor/file/strict-schema rules, then evaluates every required decision from those same bytes. No mutable shared domain model, positive cross-request cache, authority lease or externally reusable fingerprint is introduced.

For each batch, DM reads a fresh initial snapshot, locks its own document aggregates in sorted UUID order in one bounded local transaction and evaluates the complete current ACL/classification set. Existing DM mutation/ACL paths must participate in the same owning aggregate lock discipline; final classification/expected revision and ACL facts come from that local transaction. Immediately before returning, DM reads/validates the catalog AGAIN into a NEW immutable snapshot and reevaluates EVERY decision, never reuses the first positive result. Current DENY404/UNAVAILABLE503 takes precedence; if both sets allow but fingerprint changed,409 STALE_AUTHORITY requests a fresh batch rather than pretending a single unchanged generation. Same bytes are only evidence of the two actual reads, not a lease or proof no unobserved change occurred between/after them. Catalog reads are local; no remote provider/network call runs while DM row locks are held.

DM batch SQL lock acquisition<=250ms, each statement<=500ms and total endpoint<=1.5s, all capped by actual remaining time. If100 rows, catalog reread, key fetch, lock contention or serialization cannot fit, return503 and no batch success. This endpoint is metadata-only and does not mutate domain rows/audit/outbox or create commands. External profile/new port default is UNAVAILABLE503 until an independently reviewed authoritative BATCH adapter exists. A permissive scalar adapter does not enable it; no per-resource-loop fallback or local catalog wiring for an external issuer. Per-resource external replies cannot be labeled a coherent snapshot without that provider's actual reviewed consistency contract.

## KB phase and current-authority protocol

1. Authenticate actor/tenant and route action; take a coherent local complete-set/ACL/revision snapshot within500ms, then close its connection. Document snapshot create/validate requires policy.evaluate ACL ALLOW/noDENY on EVERY current collection including inactive/archived scopes. Any hidden scope404, never filter it. ACTIVE status command/no-op/replay collects EVERY current active member, not only inspectable ones. Capacity admission is bounded and cannot queue beyond50ms.
2. Initial batch calls the fixed DM endpoint ONCE with the complete distinct document set (max100); caller expected revisions are enforced where present. Validate exact actor/tenant/action, exact requested document set, all classification/ceiling facts and closed response<=32KiB. A failure aborts the whole operation. If a collection operation has no affected active members, record that exact empty local set; document policy operations still assess their requested document even when its collection membership set is empty.
3. Prepare the final complete batch with EVERY document's initial exact revision. Start ONE2-second final phase clock BEFORE dispatch. Final HTTP has<=1.5 seconds total, including response validation, and must finish with enough phase time for the<=500ms local tail. No initial ALLOW substitutes for a final batch. No SQL transaction/borrowed connection/lock is held during either HTTP call. A partial/mismatched response, timeout, late result or new unknown authority fails closed.
4. Only the live coordinator owns final SQL admission. All remote callbacks return immutable data and have NO repository/connection/transaction/executor capability. After final batch success, read current local catalog/relation facts and admit the short local transaction only while actor/request ownership and BOTH whole/final deadlines remain live. The500ms tail includes that work. Acquire local locks in order, reread COMPLETE current set and every required current ACL/noDENY, then compare captured tenant/aggregate/scope revisions. Newly hidden scope404 precedes stale409. Any changed set must fail409 rather than use staged evidence for new scopes; do not automatically retry in this request. No remote HTTP call occurs under KB SQL locks.
5. Recheck remaining budget and owner token before each SQL phase and COMMIT dispatch. Atomically commit command/revisions/audit/outbox or bounded snapshot facts. ACTIVE replay rechecks CURRENT active members and returns its original minimal receipt, without reactivation/new facts; new-key ACTIVE no-op still advances revision/audit. Final local revocation before protected serialization withholds the response, even if a previously authorized command is known committed; do not erase/reverse facts to fabricate rollback. Reconciliation always rechecks current authority.

For a SUCCESS whose COMMIT acknowledgment is observed inside the final phase, the measured DM-check→KB-commit residual is<=2 seconds because the clock began before final DM dispatch. This is the reviewed development residual bound requiring actual measured implementation evidence, not a declaration the race is narrow, all services were globally current at transmission, or production revocation controls passed. The subsequent response may take up to500ms; DM/KB remain independent transactions. Changes after each owning service's last check, including a catalog replacement immediately after its final reread, remain the explicit post-check race. No coherent cross-service generation/lease or distributed transaction is claimed.

## Cancellation and UNKNOWN COMMIT

If the initial/final assessment is slow, expired or cancelled BEFORE final SQL admission, invalidate the coordinator token, cancel pending HTTP work and ensure a late ALLOW cannot enter SQL later. Domain policy/status/revision/audit/outbox remains unchanged for that request. A callback cannot outlive its owner and obtain a new transaction. Required deterministic test releases a paused provider after HTTP timeout and proves no later transaction admission/facts.

If failure occurs in a known open transaction BEFORE COMMIT dispatch, request rollback and verify it where the connection is available. Once SQL/COMMIT is already dispatched, connection loss, timer expiry or driver cancellation may leave UNKNOWN outcome. HTTP cancellation does NOT prove rollback, absence or actual on-time commit. In particular the<=2-second acknowledged-success bound cannot be asserted for UNKNOWN commits that may finish later. Preserve original actor/tenant/operation/resource/idempotency key/canonical body; no new-key retry or fact deletion. After reconnect/restart, reconcile the same durable command outcome under FRESH complete authority: committed returns its original minimal receipt exactly once, absent allows a same-key guarded retry, different body409 only after current authorization. Withheld postcommit response may leave known committed facts while returning non-success; stale success cannot bypass current guards.

Snapshot INSERT uncertainty similarly does not fabricate a token/success or prove absence. Snapshots are private bounded evidence without a command key in this draft: preserve any committed orphan,503, and permit a new authorized request only within the10000 cap. An orphan grants no access and cannot mutate policy. Domain-mutating commands always use durable original-key reconciliation.

Required later tests: actual100-document coherent batch success; duplicate/foreign/partial/missing/extra/mismatched actor/tenant/action response failures; initial/final catalog generation change/denial/outage; scalarALLOW with unavailable batch port503; actor/global overload without queues; no SQL lock/connection across HTTP; final2-second expiration before admission; lock/statement deadlines; paused late authority result; COMMIT response loss with actual committed/absent/late-unknown branches and original-key restart recovery. Measure every timing; schema checks or mocks do not constitute actual runtime acceptance.
