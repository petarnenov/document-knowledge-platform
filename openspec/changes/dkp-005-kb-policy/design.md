ARCHIVED→ACTIVE, a new ACTIVE→ACTIVE no-op command and replay of a committed ACTIVE command all require current archive operation catalog+collection ACL and fresh DM share/classification assessment for EVERY current ACTIVE membership, initial and final. Any missing DM grant404, unknown classification/provider503, local ACL revocation404 or local aggregate/tenant revision drift409 aborts without changing status/revisions/audit/outbox. The complete active-member set cannot be filtered by caller visibility. Replays recheck that CURRENT set, then return only the original stored receipt without reapplying status or incrementing facts; an unchanged-body replay does not reject merely because its original expectedRevision is now old. New-key ACTIVE no-ops still advance revision/audit. ACTIVE→ARCHIVED is restrictive and requires its own current archive grant+ACL without remote member assessment; a later ACTIVE reactivation cannot reuse that exclusion. Concurrent addition/removal/audience/classification/status changes must pass final complete-set authority before conflicts are returned. See contracts/request-budgets.md for the remote/SQL phases and finite limits.

AudiencePolicy is immutable per collection+revision, with classification ceiling, exact allowed and denied selectors and server effectiveAt timestamp. Rule kinds: PRINCIPAL with exact issuer+subject; TENANT with exact selected owner tenant; FIRM with exact issuer+firmId; RESOURCE_SCOPE with exact issuer+resourceScopeId. Matching is `(any ALLOW) AND NOT(any DENY)` plus all other authorities. Empty ALLOW denies all. Unknown/unresolvable relations are UNAVAILABLE, never negative-to-positive fallback. Deny wins across kinds. Future scheduled effective dates are rejected in BP-04 (400 unknown field if supplied); server time determines immediate effect. Production scheduling remains a later explicit contract extension.

A membership is a server UUID, collectionId, documentId, owner tenant, sharingScope=SELECTED_TENANT, state ACTIVE|INACTIVE, revision, creator and immutable mutation reason1..1024. There is one membership identity per tenant+collection+document; reactivation changes its revision instead of creating duplicate history. A document can have many collection memberships (max50 per document), a collection max100 memberships including inactive; attempts beyond limits yield422 LIMIT_EXCEEDED atomically. New/ACTIVE association into an ARCHIVED collection returns422 INVALID_POLICY; inactivation remains possible under the same current authority. No membership operation changes DM ACL, classification, lifecycle, version or active pointer. Metadata-only membership does not mean the document is processed, reviewed or published.

KB domain is framework-free. Application owns CollectionRepository/KBUnitOfWork, KnowledgeAuthorityPort, AudienceRelationPort, DocumentShareBatchAuthorityPort and SnapshotTokenPort abstractions. Adapters implement JDBC, bounded catalogs and fixed HTTPS DM calls. No dependency on DM implementation/classes/database entities; only versioned wire contracts. No KB imports into identity-contracts. BFF imports generated DTOs rather than domain code. Logical database `knowledge_base`, schema `kb`, distinct migrator/runtime credentials; no DM or Search schema grants, shared SQL connections or cross-database FKs.

## Revision snapshots and concurrency

Each affected collection stores separate monotonically increasing membershipRevision and audiencePolicyRevision; collection status/ACL mutations also advance aggregateRevision. Any audience/membership/status/ACL mutation increments a KB-owned tenantPolicyRevision fence and affected document membership-set revision(s) atomically, with immutable policy revision/history/audit/invalidation/outbox facts. An audience mutation affecting active members increments all affected document-set revisions. Never reset/reuse revision numbers after restart, archive, no-op or remove/re-add. Overflow fails503 without mutation. Row/tombstone histories survive deactivation.

Serialize policy-affecting mutations by locking the owning tenant fence, then collection rows sorted UUID, then document membership-scope rows sorted UUID, then command rows. This is a local KB transaction lock, not a cross-service/distributed lock. Initial evaluation reads the complete set/fence/ACL from one coherent bounded MVCC snapshot and closes its connection before remote batch assessment. Only the final local phase takes ordered locks and rechecks the complete current set; no filtered/paged set may stand in for policy completeness. DM reads and final authority checks remain independently transactional.

POST `/api/v1/knowledge/documents/{documentId}/policy-snapshots` requires knowledge.policy.evaluate grant, explicit current DM share authority and own selected tenant. At initial read and final transaction/response boundary the current actor MUST have knowledge.policy.evaluate catalog grant AND exact knowledge.policy.evaluate ACL ALLOW without DENY on EVERY referenced collection. No collection IDs, rule details, counts, actor details or hidden scopes leak.
