## Catalog and conjunctive authorization

New technical adapter module `modules/authorization-catalog` implements existing ResourceAuthorizationPort without adding claims or shared domain entities. Explicit configured absolute file path; admin-controlled, git-ignored read-only file mounted only where used. Local bootstrap generates synthetic BP-01 actor grants from verified issuer/subject configuration; browser input cannot write or select it. Enforce regular file/no symlink, owner-controlled non-group/world-writable path, bounded 64KiB file, strict JSON schemaVersion=1, max100 entries, max32 actions per entry, all fields bounded. Entry keys are exact issuer/subject/tenant; reject duplicates, unknown fields/actions, wildcard, generic role or implicit owner interpretation. Optional delegation ceiling is an enumerated subset of known actions. Committed examples are secret-free schema/examples, never operational grants or credentials.

Read/validate per decision and again at final authority boundary; no stale positive cache across reads. Missing/unreadable/oversize/partially-written/malformed/schema-mismatched file produces UNAVAILABLE/503. Administrator replaces catalog atomically. External profile never wires catalog; unavailable adapter503. Fixed route-boundary order: (1) BP-01 session/tenant membership; (2) catalog load, malformed/unavailable503 before any decision; (3) route operation grant: list, create and every mutation lacking it403 before any lookup; GET detail/ACL lacking document.inspect-draft or GET legal-holds lacking document.legal-hold.inspect404 before any lookup; (4) lookup+ACL: no ALLOW, explicit DENY or missing document identical404; (5) expectedRevision mismatch409 only after step4 passed. Catalog present but no exact issuer/subject/tenant entry is DENY at step3. Ordinary document.read never substitutes for inspect-draft.

Create has no existing ACL: document.create catalog grant authorizes an atomic server-derived creator ACL bootstrap, not implicit ownership. Explicit bootstrap entries allow only the creator's catalog-granted resource actions (exclude create/read), intersected with applicable BP-02 actions; no role/other-tenant grants. No ACL can bypass a missing catalog grant. All existing-resource commands require operation ALLOW AND current DM-owned ACL allow; explicit denies override. No broad admin privilege. Final inspection/list response rechecks current catalog+ACL, with documented narrow post-check network race.

DM application owns an abstract DelegationPolicyPort for exact target/action/ceiling validation, implemented by the same bounded catalog reader; do not add domain delegation types to identity-contracts or infer a ceiling from ResourceAuthorizationPort ALLOW alone.

ACL mutation is PATCH .../acl (PUT removed), with {expectedRevision, mode:RESTRICT|DELEGATE, changes:[{operation,principal,action}]}. changes min1/max100; operation enum ADD_ALLOW|REMOVE_ALLOW|ADD_DENY|REMOVE_DENY. No wildcard/group/tenant-wide principal. The exact (principal.issuer,principal.subject,action) key MUST be unique across the entire delta regardless of operation, else422 DUPLICATE_ACL_CHANGE before transaction.

Rule identity is exact (principal,action,effect). ADD of an existing exact rule and REMOVE of an absent exact rule are per-entry no-ops; the command still commits, increments revision and writes audit facts. Apply the whole delta atomically, preserve unrelated rules, then enforce resulting unique-rule count<=100; overflow422 ACL_RULE_LIMIT with no partial write.

RESTRICT requires document.acl.restrict catalog operation grant AND current ACL ALLOW, no DENY. Every entry MUST target caller and operation REMOVE_ALLOW or ADD_DENY; otherwise422 RESTRICT_SCOPE. Never touch another principal or remove any DENY. A RESTRICT removing the caller's own document.acl.restrict ALLOW commits and returns its minimal receipt because precommit authorization passed; later replay/new-command authorization fails404.

DELEGATE requires document.acl.delegate catalog operation grant AND current ACL ALLOW, no DENY. All four operations are permitted only when target principal has exact same-tenant catalog entry granting the action AND action is within caller's explicit delegation ceiling. Target not grantable422 TARGET_NOT_GRANTABLE; outside ceiling403 DELEGATION_CEILING. Target may be caller. ADD_ALLOW never clears DENY; REMOVE_DENY is available only through this ceiling-constrained path. Third-party REMOVE_ALLOW/ADD_DENY likewise require this bounded path. All checks precede transaction changes; aggregate mutation/revision/audit/idempotency commit together. Actor/tenant identities never derive authority from forwarding headers. Legal-hold operations require their own operation+ACL permission, no generic admin shortcut.
